# ADR-0033 — 별표 코드는 시스템이 채번한다 (`AX000001`)

> 상태: 채택 · 날짜: 2026-09-09

## 맥락

[[ADR-0005-코드-표시명-이중체계]]는 「코드는 시스템 자동 채번 · 유저 입력 불가 · 불변」을 세웠고,
구분자(`D0001`) · enum(`E0001`) · 공용조항(`C0001`) 이 그 규칙을 따른다.
별표만 예외였다 — 〔D-P4-23〕이 「코드는 유저 입력 · 등록 후 불변 · 중복 거부」로 정했다.

예외를 둔 이유는 별표가 실물 약관에서 이미 이름 붙은 표라는 감각이었지만, 실제로 남은 것은
`APX01_INTEREST` · `APX05` · `APX21_FRACTURE_TABLE_2` 처럼 **사람마다 다른 규칙으로 지어진 문자열**이다.
게다가 별표 번호는 상품 별표 목록의 순서로 따로 계산되므로([[ADR-0030-별표번호-상품목록순서]])
코드 안의 `01` · `21` 은 번호를 뜻하지도 않으면서 번호처럼 읽힌다.
등록 화면은 유저에게 「다음 번호가 몇 번인지」를 스스로 찾아 중복을 피하라고 요구하고 있었다.

## 결정

- 별표 코드는 **시스템 자동 채번** — 접두 `AX` + 최소 6자리 순번, `AX000001` 부터.
- 순번의 출처는 카탈로그 · 공용조항과 같은 `code_sequences` 테이블. kind `appendix`, scope 는 전역(`""`).
  순번은 오르기만 한다 — 삭제된 코드는 다시 태어나지 않는다.
- 등록 입력에서 `code` 를 없앤다(`NewAppendix` 에 code 없음 — 타입으로 강제). 등록 후 코드는 불변.
- 코드가 시스템 것이 되면서 **중복 거부 규칙은 사라진다** — 같은 코드가 두 번 나올 수 없다.
  이름 중복은 여전히 허용한다 (별표는 이름으로 식별하지 않는다).
- 〔D-P4-23〕의 「유저 입력」 절반을 폐기한다. 「등록 후 불변」은 그대로다.

## 이유

코드는 참조의 정본이지 사람이 읽는 이름이 아니다([[ADR-0005-코드-표시명-이중체계]]).
사람이 지어야 할 것은 이름(`장해분류표`)이고, 식별자는 기계가 붙이면 된다 —
별표만 예외로 두면 마스터 4종 중 하나만 다른 규칙으로 사는 셈이고,
그 예외의 대가는 「중복을 피할 책임」이라는 형태로 유저가 치른다.

## 버린 대안

- **유저 입력 유지 + `AX\d+` 형식만 강제** — 화면 표기는 가지런해지지만 다음 번호를 찾는 일은
  여전히 유저 몫이고, 중복 거부 · 빈 번호 같은 사고가 그대로 남는다. 형식 검사는 문제의 절반만 푼다.
- **자릿수 4 (`AX0001`)** — 다른 코드(D · C · E)와 같은 폭. 별표는 상품마다 20건대이지만
  전상품 superset 이라 자릿수를 넉넉히 두는 편이 낫다고 보아 6자리로 정했다 (초과하면 자연 확장).

## 결과와 감수하는 비용

- **기존 코드는 전부 갈아엎힌다.** 시드(알파Plus)의 별표 21건이 `APX01_INTEREST` → `AX000001` …
  `AX000021` 로 바뀌고, 그것을 가리키는 문면(보통약관 · 담보약관 트리)의 별표 참조 슬롯과
  상품 별표 목록, E2E 스펙의 기대 코드도 함께 바뀐다. 마이그레이션 대상 운영 데이터는 아직 없다.
- 코드에 뜻(`_DISABILITY`)이 사라져 시드 JSON 만 보고는 무슨 표인지 알 수 없다.
  대신 `appendices.json` 의 `code` 를 남겨 **채번 순서가 어긋나지 않았는지 대조**하는 데 쓴다
  (시드 로더가 `expectCode` 로 검사한다 — 공용조항 시드와 같은 방식).
- 도메인 순수층의 별표 픽스처(`APX_BURN` 등)는 그대로 둔다 — 그 층에서 코드는 불투명한 문자열이고,
  실제로 코드를 만드는 자리는 `createAppendix` 하나뿐이다.
