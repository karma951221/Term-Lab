# ADR-0032 — 구분자 종류의 화면 명칭: 「유형」 · 「일반」 (Q-B 번복)

> 상태: 제안 · 날짜: 2026-09-09
>
> [[02_UI/화면/구분자_화면기획]] Q-B(2026-09-06 확정)를 뒤집는다. **미해결 충돌이 남아 있다** — 아래 §열린 문제.

## 맥락

2026-09-06 에 `scalar` 의 화면 라벨을 **「단일값」**으로 확정하면서 「일반」을 명시적으로 버렸다
— 이유는 「일반은 폼이 아닌 것으로 읽히기엔 흐리다」였다.

2026-09-09 화면 검토에서 두 가지가 다시 걸렸다.

- **「종류」라는 필드명이 어색하다.** 앱 안에서 「종류」는 담보속성 종류 · 문서 종류 · 노드 종류에도 쓰여
  구분자 전용 단어가 아니다.
- **「단일값」이 값의 개수를 말한다.** 폼이 목록에서 빠진 뒤([[ADR-0031-폼-구분자목록-분리]])
  대비 대상이 상수 · 파생이 됐는데, 이 셋을 가르는 축은 「값이 몇 개냐」가 아니라
  「사람이 채우냐 · 마스터에 있냐 · 계산되냐」다. 「단일값」은 없어진 대비를 가리키는 이름이 됐다.

## 결정

- 필드명 **「종류」 → 「유형」**.
- `scalar` 의 화면 라벨 **「단일값」 → 「일반」**.
- 「폼」 · 「상수」 · 「파생」은 그대로. 도메인 용어(`scalar` · `struct`)도 그대로.
- 라벨은 계속 `src/app/_lib/labels.ts` 의 `KIND_LABEL` 한 곳만 통과한다.

## 이유

폼이 목록에서 빠지면서 Q-B 를 정할 때의 전제(「일반 vs 폼」을 갈라야 한다)가 사라졌다.
남은 셋에서는 「일반」이 「특별한 사정이 없는 보통의 구분자」로 바로 읽힌다.

## 버린 대안

- **「단일값」 유지** — 폼이 화면에서 사라진 뒤로는 무엇에 대한 「단일」인지 화면에 근거가 없다.
- **「값형」 · 「입력형」** — 상수도 값이고 파생도 값이라 가르는 힘이 없다.

## 열린 문제 — 「유형」이 세 가지를 가리킨다

이 결정이 만든 충돌이며 **아직 닫지 못했다.**

| 자리 | 「유형」이 가리키는 것 |
|---|---|
| 좌측 내비 **유형** (`/types`) | 선택지 · 폼 |
| 구분자 목록 · 상세의 **유형** 컬럼 | 일반 / 상수 / 파생 |
| 새 구분자의 **타입** 필드 | 문자열 / 숫자 / 예·아니오 / 날짜 / 선택형 |

구분자 목록 화면에서는 좌측 내비의 「유형」과 컬럼 헤더 「유형」이 나란히 서고,
생성 화면에서는 「유형」 바로 아래 줄이 「타입」이다 — 한국어에서 유형과 타입은 같은 말이다.

후보 —
- ⓐ **「타입」을 바꾼다** — 구분자의 분류가 「유형」을 갖고, 값이 무엇인지는 「값 종류」 같은 다른 말로.
- ⓑ **내비 「유형」을 바꾼다** — 그 탭이 담은 것은 선택지와 폼이니 「타입 정의」 · 「입력 형식」이 실제에 가깝다.
- ⓒ **그대로 둔다** — 세 자리가 화면상 멀다고 보고 감수. 다만 구분자 목록에서는 멀지 않다.

닫히기 전까지 이 ADR 은 **제안** 상태로 둔다.
