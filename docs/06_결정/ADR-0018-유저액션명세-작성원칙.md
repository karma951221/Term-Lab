# ADR-0018 — 유저액션 명세의 축과 경계

> 상태: 확정 · 최종수정: 2026-09-02

## 맥락

기획 6문서와 QA 시나리오 13건이 합의 수준에 올랐고, `02_UI/` 는 빈 뼈대다.
"사람이 무엇을 할 수 있나"가 아직 어디에도 전수로 적혀 있지 않다.
시나리오는 **대표 흐름**만 담기 때문에, 흐름에 안 걸린 액션(삭제·순서 변경·관계 끊기)이
조용히 빠진다. 그 상태로 화면 설계에 들어가면 화면이 누락을 상속한다.

문제는 새 문서를 어디에 어떤 축으로 두느냐다. 시나리오·화면기획과 겹치면 셋 다 썩는다.

## 결정

**대상(도메인 객체) 축 · 의도(커맨드) 단위**로 `docs/02_UI/유저액션/` 에 쓴다.

1. **축은 객체** — 화면이 아니라 구분자·담보·문면·상품담보 같은 도메인 객체마다
   "이 객체에 사람이 할 수 있는 일"을 전수로 적는다.
2. **입도는 의도** — 저장소 상태를 바꾸는 의도 하나가 액션 하나. 클릭·드래그·모달 같은
   UI 제스처는 적지 않는다. UI 진입경로는 `> 진입경로(잠정)` 한 줄로만 부기하고,
   화면기획이 생기면 지운다.
3. **조회도 액션이다** — 완결성 조회·사용처 추적·사전평가처럼 바꾸지 않고 보는 것도 포함하되,
   결과 열에 `바뀜 없음` 을 명시해 쓰기 액션과 구별한다.
4. **파일은 기획 영역(feature) 단위**, 객체는 파일 안의 섹션 단위.
5. **완전성은 두 방향으로 검사** — 9종 체크리스트 훑기(해당없음도 명시) + 시나리오 역방향 대조.

## 버린 대안

- **화면 단위** — 화면목록이 빈 표라 축을 지금 잡을 수 없다. 화면이 바뀔 때마다 명세가 같이 썩고,
  `_템플릿/화면기획.md` 의 「조작과 상태 전이」 절과 정면으로 겹친다.
  → 화면기획은 나중에 이 명세를 **소비**한다(어느 화면이 어느 액션을 담는지 매핑).
- **행위(동사) 단위** — 권한·모드 규칙을 한자리에 모으기엔 좋지만 기획 문서와 대응이 흐려져
  누락 검사가 사람 눈에 의존하게 된다.
- **의도 + UI 제스처 2층 전면 기재** — 정보량은 최대지만 화면기획과 중복 관리 지점이 두 곳
  생긴다. 제스처 층은 `진입경로(잠정)` 한 줄로 축소했다.

## 감수하는 비용

- 객체 축이라 **하나의 사용자 흐름이 여러 파일에 흩어진다.** 흐름을 보려면 시나리오를 봐야 한다
  — 그래서 역방향 대조를 완전성 검사에 넣었다.
- **진입경로 부기가 화면기획 확정 전까지 부정확**하다. 잠정 표기로 두고, 화면기획이 생기는 순간
  삭제하는 것으로 수명을 못박았다.
- 초안은 기획에 답이 없는 자리를 **임의 결정으로 채운다.** 각 파일의 `## 임의 결정` 표에
  모아 두고 확정 대화로 걷어낸다 — 걷히기 전까지는 명세가 합의된 내용처럼 읽힐 위험이 있다.
